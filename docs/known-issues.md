# Known Issues & Assumptions

This document tracks known edge cases, temporary limitations, and architectural assumptions made during development.

## Assumptions

1. **Local Host Worker Execution**: The judge worker runs on the developer's host machine to ensure the Docker daemon socket is never exposed or mounted into containers.
2. **Docker Desktop on Windows**: Container sandboxes require Docker Engine running locally with Linux containers enabled (WSL2 backend recommended).
3. **Execution Language**: Node.js / JavaScript (ES2022) is the initial target language inside the `node:20-alpine` sandbox image.

## Open / In-Progress Items

- Docker Desktop must be running on the host machine to execute container sandboxes and `pnpm test:safety` / `pnpm test:integration`.
- **DNS resolution inside `--network none` (`SAFE-04`)**: Asynchronous DNS lookups (such as `http.get('http://google.com')` in `attack-suite/network-attempt/index.js`) may block waiting for DNS timeout rather than failing immediately, resulting in `TIME_LIMIT_EXCEEDED` instead of `RUNTIME_ERROR`. Direct IP socket connections fail immediately with `ENETUNREACH` (`RUNTIME_ERROR`); both completely prevent network access.
- **Disposable `--rm` containers & `OOMKilled` inspection (`SAFE-02`)**: Because sandbox containers run with `--rm` for leak-proof cleanup, Docker deletes container metadata immediately on exit. `classifySandboxOutcome` therefore combines external wall-clock timeout flags (`timedOut` / `execFileTimedOut`), output-limit flags (`outputExceeded` / `ERR_CHILD_PROCESS_STDIO_MAXBUFFER`), runtime OOM messages (`heap out of memory`, `MemoryError`), and an explicit `oomKilled` guard so non-OOM `SIGKILL`/exit `137` conditions are not blindly misclassified as `MEMORY_LIMIT_EXCEEDED`.
- **Problem Management Scope (Day 12)**: `PUT /api/problems/:id` updates public problem metadata (`title`, `statement`, `difficulty`, `tags`, limits, sample I/O) and preserves existing MinIO test-case objects; dedicated endpoints for mutating individual hidden test cases after creation are deferred. Additionally, `DELETE /api/problems/:id` archives (`is_archived = true`) rather than hard-deleting problems that already have submissions, preserving submission history and MinIO test objects.
- **Refresh Tokens Deferred (Day 14)**: Authentication uses a single `HttpOnly` JWT cookie without a refresh-token endpoint; when the cookie expires, `apiClient.ts` triggers a single session-expiration redirect to `/login`. Rotating refresh tokens remain a future enhancement.
- **Submission History Deferred & Redis Pub/Sub Limits (Day 16)**: Live verdict updates on `ProblemDetailPage` use SSE (`EventSource`) with bounded polling fallback; a full submission history page remains planned for later days. Because Redis Pub/Sub is non-durable (no event replay log), SSE recovers missed events via a fresh PostgreSQL snapshot on connect/reconnect and falls back to polling if Pub/Sub disconnects.
- **Leaderboard Scope & Cache-Aside (Day 17)**: Global leaderboard uses Redis Sorted Sets with a composite float score (`problemsSolved * 10,000,000 + (9,999,999 - penalty)`), breaking ties by lower penalty seconds and secondary tie-breaking by username and userId. When Redis is unavailable or empty, the API computes standings on-demand directly from PostgreSQL `submissions` (`verdict = 'ACCEPTED'`), strictly ordering by `createdAt ASC` for idempotent first-solve penalty attribution.
- **Contest Scoreboard Freeze Precision & Unfreeze Reconciliation (Days 18 & 19)**: During the freeze window, submissions are judged immediately and persisted in PostgreSQL, but public contest standings reflect the pre-freeze state. When the contest concludes and the admin unfreezes the scoreboard, standings are recalculated from the full submission set. In high-concurrency contest finishes, unfreezing triggers a batch recalculation that may momentarily load Redis/PostgreSQL; this is mitigated by distributed locking on the rebuild operation.
- **Notification Reconciliation Backlog & Distributed Locking (Day 20)**: Background sweeper processes unnotified completed submissions in batches of up to 1,000 rows. If more than 1,000 unnotified submissions exist, the remaining backlog is processed in subsequent scheduler cycles. The sweeper uses a distributed Redis lock with a heartbeat watchdog; if lock renewal fails (e.g. during a Redis failover or network partition), the sweep immediately stops initiating new work to prevent dual-processing.
- **Production Docker Socket Mount & Sibling Container Trade-Off (Day 22)**: In `docker-compose.prod.yml`, the worker service mounts `/var/run/docker.sock` to orchestrate sibling disposable sandbox containers. While untrusted user code runs inside strictly isolated containers without socket access, compromising the worker container itself would grant root access to the Docker daemon. For enterprise multi-tenant deployments, worker nodes should run on dedicated VMs or use microVM runtimes (Firecracker/gVisor).
- **Reverse Proxy Buffering for Server-Sent Events (Day 22)**: When deploying behind Nginx or another reverse proxy, proxy buffering must be explicitly disabled (`proxy_buffering off; proxy_cache off;`) for `/api/submissions/:id/live` and `/api/contests/:id/live`; otherwise, events are buffered until the buffer fills or connection closes, breaking real-time feedback.
- **Fail-Open Policy for Auth Rate Limiting (Day 11 & Day 22)**: If Redis becomes unreachable, login lockout counters fail open (allowing password verification against PostgreSQL) rather than denying all users access. Strict password validation via bcrypt is preserved at all times.
